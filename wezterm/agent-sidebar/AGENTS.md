# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`agent-sidebar` is a small Go/Bubble Tea TUI, run inside a dedicated narrow WezTerm pane, that renders a live list of every pane running a coding agent (Claude Code, Codex) and its status (working/blocked/done/idle). It has a second mode, `agent-sidebar setup`, that wires the hook plumbing into Claude Code's and Codex's config so they report status in the first place.

This directory is one part of a larger data pipeline that spans the parent `wezterm/` directory:

1. **`../scripts/agent-status.sh <status> <agent-name>`** — invoked as a Claude Code / Codex hook (see below). It resolves the pane's tty via `wezterm cli list --format json` + `jq` (hook subprocesses have no controlling terminal, so `/dev/tty` doesn't work) and writes `agent_status` / `agent_name` as WezTerm user vars via an OSC 1337 `SetUserVar` escape sequence.
2. **`../wezterm.lua`** (`write_agent_status_snapshot()`) — WezTerm-side Lua that reads every pane's user vars across all workspaces and writes them to `$HOME/.cache/wezterm/agent-status.txt`, one line per pane: `workspace\tstatus\tagent_name\ttab_number\ttitle\tpane_id`. `tab_number` is the pane's 1-based position within its window's tab list (`ipairs(w:tabs())`), shown in the sidebar as `(tab:N)`. It skips any pane whose `agent_sidebar` user var is set (see `announceSelf()` below) so the sidebar never lists itself, and also skips any pane whose foreground process is no longer the agent CLI (`has_live_agent_process()`, checked via `pane:get_foreground_process_name()`) so an entry disappears once the agent actually exits rather than lingering on `agent_status`'s last value — hooks alone can't catch an abrupt exit (e.g. Ctrl+C), since no hook fires in that case. That liveness check requires `AGENT_MISSING_GRACE_TICKS` (3) consecutive misses before actually dropping a pane (`pane_agent_is_live()`, state kept in module-level `agent_missing_ticks`), since a single miss can be a transient false negative (an interactive subprocess briefly taking the pty's foreground process group, or the fork/exec window at CLI startup) rather than a real exit — removing and re-adding an entry on every such blip was churning the AGENTS list's row layout enough to visibly ghost the sidebar's rendering and throw off click-to-focus row hit-testing. `pane_id` lets the sidebar focus a pane on click via `wezterm cli activate-pane --pane-id`.
3. **This program** — polls that snapshot file every 500ms and renders it, grouped by workspace.

There is no direct IPC between this program and WezTerm; the snapshot file is the only interface. `agent-sidebar` cannot read WezTerm user vars directly (`wezterm cli list` does not expose them).

## Commands

```sh
go build .                # build the agent-sidebar binary
go test ./...              # run all tests
go test -run TestEnsureHooksIsIdempotent .   # run a single test
go vet ./...
```

There's no separate lint config; `go vet` is the extent of it.

## Code architecture

- **`main.go`** — the TUI (`model`/`Update`/`View` per Bubble Tea's Elm architecture). `loadEntries()` parses the tab-separated snapshot file; a malformed or short line is silently skipped rather than erroring, since the snapshot writer is trusted but the file could be mid-write. `renderIcon` swaps in a live spinner for `"working"` status and static emoji for the rest; entries with no status are never written to the snapshot in the first place, so every status seen here is one of the known ones. The alt screen (`tea.WithAltScreen()`) is required, not cosmetic — inline rendering desyncs on pane resize. `announceSelf()` sets its own `agent_sidebar` user var on startup for the Lua side to filter out. `Update()`'s `tickMsg` branch re-polls the pty's real size via `term.GetSize()` every tick rather than trusting `tea.WindowSizeMsg` alone — a `top_level` split (see `../wezterm.lua`) doesn't reliably deliver an accurate resize event for the newly-created pane, which left `m.width` stuck too wide and drew the section-divider rule past the pane's actual right edge into whatever pane sits beside it. `waitTransitions()` (a pure function, unit-tested in `main_test.go` without shelling out) diffs each tick's statuses against `model.prevStatus` and reports only panes that just entered `blocked`/`done` (`waitStatuses`), so a pane that's been sitting in a wait state for many ticks — or already was one at startup, since `initialModel()` seeds `prevStatus` from the first snapshot — doesn't re-fire a notification every 500ms. Each reported transition raises a macOS notification via `notifyCmd()` (`osascript`, values passed as `argv` items rather than interpolated into the AppleScript source, so a window title containing quotes can't break out of the script), unless its pane is the one the user is currently looking at per `focusedPaneID()`. That check reads `wezterm cli list-clients`' `focused_pane_id` rather than `wezterm cli list`'s per-pane `is_active`, since `is_active` marks one pane per *tab* — true for every tab's own active pane simultaneously — and can't tell you which single pane is actually on screen across tabs/windows; `focused_pane_id` is per-client global state. `focusedPaneID()` is only invoked when `waitTransitions()` actually found something, not on every tick, so the sidebar doesn't shell out to `wezterm cli` twice a second for nothing. `waitTransitions()`'s detection is per-process (`model.prevStatus` is in-memory), so with multiple `agent-sidebar` instances running at once (e.g. one per WezTerm window, all polling the same snapshot file) each would otherwise fire its own notification for the same transition. `claimNotification()`/`pruneNotificationMarkers()` dedupe that cross-process via marker files under `notifiedMarkerDir()` (`~/.cache/wezterm/agent-notified/<paneID>`, next to the snapshot file): claiming uses `os.O_CREATE|os.O_EXCL`, which is atomic at the filesystem level, so exactly one instance's create call wins when several race to claim the same pane on the same tick. A claimed marker is removed once its pane leaves the wait state (or vanishes from the snapshot entirely) so the next blocked/done occurrence for that pane can be claimed - and therefore notified - again, rather than that pane going permanently silent after its first notification.
- **`setup.go`** — `agent-sidebar setup` merges hook entries into Claude Code's `settings.json` and Codex's `hooks.json`. Both tools share the same hook event names and JSON shape (`hookSpecs`), so one merge function (`ensureHooks`) drives both targets. Merging is additive and idempotent by design: it decodes into a generic `map[string]interface{}` tree (not a typed struct) specifically so unrelated existing keys/hooks in the user's config survive untouched, and re-running setup checks for an exact command-string match (`hookCommandPresent`) before appending so it never duplicates an entry. `$CLAUDE_CONFIG_DIR` and `$CODEX_HOME` are honored when present instead of hardcoding `~/.claude` / `~/.codex`.
- **`setup_test.go`** — covers `ensureHooks` from-scratch creation, idempotency, and preservation of pre-existing unrelated config, plus the env-var path overrides.

## Conventions worth knowing before editing

- Any change to the snapshot file's line format (`workspace\tstatus\tagent_name\ttab_number\ttitle\tpane_id`) must stay in sync with `write_agent_status_snapshot()` in `../wezterm.lua` — they're two independent implementations of the same wire format, not something this repo can typecheck across. `loadEntries()` splits `pane_id` off the end of the line (not via one `SplitN`) so a title containing a literal tab still parses correctly.
- Any change to `hookSpecs` (event names/status mapping) changes what real Claude Code / Codex config files get merged into on the user's machine — `ensureHooks` is meant to be safe to re-run, so preserve that idempotency guarantee when touching it.
- The file-change log (`../scripts/agent-filechange.sh`, `$HOME/.cache/wezterm/agent-file-changes.log`, format `file\tagent\t+added\t-removed\tpane_id`) is a second independent wire format with the same hand-sync requirement. `pane_id` there comes straight from `$WEZTERM_PANE` (no `wezterm cli` lookup needed, unlike `agent-status.sh`'s tty resolution) since that env var already *is* the pane id.
- Both the AGENTS and CHANGES sections are click-to-focus: `agentUnits()`/`changeUnits()` build the exact same line layout used for both rendering and `paneIDAtRow()`'s hit-testing, so they can't drift apart. A click resolves to `wezterm cli activate-pane --pane-id <id>` via `activatePaneCmd()`.
- `truncate()` must bound *display* width (`github.com/charmbracelet/x/ansi`'s `Truncate`/`StringWidth`), not rune count: a title with wide characters (CJK, emoji - common in window titles) can fit within the rune budget yet overflow the pane's actual column width, wrapping onto a second physical terminal row. `paneIDAtRow()` has no way to know about that extra wrapped row, so every row below it resolves to the wrong pane on click. `TestTruncateBoundsDisplayWidthNotRuneCount` in `main_test.go` guards this.
